# OAuth Provider configuration and sign-in

Configure an OAuth provider through the normal Provider API or administration
page, then enable its qualified `owner/name` entry in an application. Sign-in
and explicit account linking use the same configured scopes, browser-bound
state, provider identity and current configuration checks.

## Native configuration

The native Provider API accepts `custom_auth_url`, `custom_token_url`,
`custom_user_info_url`, `scopes` and `user_mapping`. `user_mapping` accepts either
a JSON object or a JSON string encoding that object. The stored representation
is JSON text; the native response exposes the mapping as an object. Compatibility
requests also accept the corresponding camelCase field names.

For a `Custom` provider, and for the explicit-endpoint generic OAuth/OIDC path,
provide all three URLs. An `OIDC` provider can instead use issuer discovery as
described below. URLs must be HTTP(S), have a host, contain no userinfo or
fragment, and be at most 4096 bytes. Existing authorization URL query parameters
are retained; Casdog replaces its own `client_id`, `redirect_uri`,
`response_type`, `state` and `scope` parameters rather than adding duplicates.
The callback destination is generated by Casdog and cannot be overridden by a
caller-supplied redirect URI.

## Token and UserInfo URL templates

Custom/generic OAuth supports Casdoor placeholders written as `{name}`. Names
start with an ASCII letter or underscore, followed by letters, digits or
underscores. Authorization URLs do not support placeholders: client secrets
and PKCE verifiers must never be sent in a browser authorization URL.

A token template may use `clientId`, `clientSecret`, `code`, `redirectUri`,
`codeVerifier` and `state`, only in query parameter **values**. For example:

```text
https://idp.example/token?appid={clientId}&secret={clientSecret}&code={code}&redirect={redirectUri}&verifier={codeVerifier}
```

Casdog expands and percent-encodes the values, removes the complete query from
the HTTP request URL, and POSTs that query as an
`application/x-www-form-urlencoded` body. A `{codeVerifier}` placeholder enables
S256 PKCE. A token URL without placeholders uses the normal OAuth authorization
code form, with `code_verifier` added when PKCE is enabled.

UserInfo templates may use `clientId`, `state`, `access_token` and identifier
names from the token response's top-level extra fields, for example:

```text
https://idp.example/user?access_token={access_token}&openid={openid}&appid={clientId}
```

Values must be nonempty strings, booleans, or signed/unsigned 64-bit integers;
objects, arrays, null, floating-point values and missing fields fail before
the UserInfo request. UserInfo placeholders can appear in path segments or
query values, never the authority, port or parameter names. Path traversal
segments are rejected. Each replacement is percent-encoded, so token values
cannot inject a host, query parameter or fragment. UserInfo templates carry
their configured credentials and omit the automatic Bearer header; ordinary
UserInfo URLs use Bearer authentication. A templated UserInfo URL deliberately
sends its query credentials to that configured server: configure a trusted
HTTPS endpoint and avoid query logging there.

There are at most 32 placeholders per URL, each expanded value is at most
16384 bytes, and the expanded request target/form is at most 65536 bytes.
Token extras exist only in the callback request, between token exchange and
UserInfo; no process-local token cache is used or required.

## OIDC issuer discovery and PKCE

For `type: "OIDC"`, set `domain` to the complete issuer base, or use
`issuer_url` if `domain` is empty. Issuer paths are preserved, for example
`https://idp.example/tenant`. Before creating browser state, Casdog fetches
`<issuer>/.well-known/openid-configuration`. The returned `issuer` must match
the configured normalized issuer exactly; the normalized base has no trailing
slash. Query parameters, fragments, userinfo and issuer templates are rejected.
HTTPS is required; explicitly approved loopback HTTP is available for local
integration tests.

Discovery must supply authorization and token endpoints unless the
corresponding explicit custom URL overrides them. Without a JWKS URL it also
requires UserInfo. A discovered JWKS URL enables verified ID-token identity,
including ID-token-only sign-in when UserInfo is absent. Discovered URLs cannot contain templates;
explicit overrides can use the token/UserInfo templates above. Discovered
server endpoints pass the same DNS, response-bound and approval checks as
explicit endpoints. Private-network approval applies to the issuer origin and
explicitly configured server endpoint origins, not an arbitrary new private
origin named by a discovery document.

S256 advertised by discovery enables a server-generated PKCE verifier. A
server-generated nonce is always sent for issuer-based OIDC. The endpoint
snapshot, verifier, nonce, start time and approval/configuration bindings are persisted
with the one-use browser state in PostgreSQL. Another instance can complete
the callback without fetching mutable discovery metadata again. Changed local
configuration or revoked approval requires a new flow. Discovery alone does
not authenticate users: token exchange must lead to verified ID-token claims
or authenticated UserInfo as described below.

### ID-token signature and identity checks

When discovery supplies `jwks_uri`, an ID token is required and verified before
profile mapping. Casdog fetches the public JWKS through the checked HTTP client
on each callback; it does not reuse an unbounded or process-local key cache.
JWKS responses use the same 1 MiB response bound, timeouts and redirect refusal.
At most 32 keys are accepted. Private JWK components, symmetric keys, ambiguous
matching keys, incompatible `alg`/`use`/`key_ops`, weak RSA keys and invalid EC
points are rejected. Accepted signatures are RS256/384/512, PS256/384/512 and
ES256; RSA moduli must be 2048–8192 bits with a public exponent of at most
32 bits, and ES256 requires P-256. HMAC,
`none`, unsupported curves/algorithms and token-supplied key URLs are rejected.
The algorithm must also be advertised by discovery (RS256 is the default when
the metadata field is absent). Duplicate JSON members in JOSE, claims and
JWKS documents are rejected.

Verified claims must bind the exact issuer, client audience, authorized party
(`azp` for multiple audiences, and any supplied `azp`), nonempty string subject,
expiration, issuance time and the nonce saved with the browser state. Clock
skew is at most 30 seconds; issuance cannot predate flow creation by more than
60 seconds. Flows older than 600 seconds cannot validate identity, and the
normal one-use browser state expires after five minutes. `nbf` is checked when
present. An optional `at_hash` must match the actual access token using the
signature algorithm's hash family.

If UserInfo is present, its string `sub` must equal the signed ID-token `sub`.
UserInfo then overrides corresponding profile claims. Missing or invalid ID
tokens cannot fall back to UserInfo when JWKS identity verification is enabled.
If UserInfo is absent, only the verified ID-token claims can create the
profile; decoding a JWT without signature verification never authenticates a
user. Configure the `openid` scope when requesting ID tokens. Providers without
JWKS retain the authenticated UserInfo path and cannot use ID-token-only login.

JWKS URLs cannot contain templates. Their private-network approval is limited
to already approved issuer/explicit server origins. With custom headers, JWKS
must share the issuer origin, so discovery cannot forward those secrets to an
undeclared server. The callback rechecks current configuration and approval
separately before token, JWKS and UserInfo requests; final linking and MFA
redemption retain their current configuration/grant checks.

### Token endpoint client authentication

Generic OAuth/OIDC accepts `method` values `client_secret_basic`,
`client_secret_post` and `none`. Historical `POST`/`post` means
`client_secret_post`. For OIDC, an explicit method must appear in discovery's
`token_endpoint_auth_methods_supported`. With no configured method, Casdog
selects an advertised supported method in basic, post, none order; missing
metadata defaults to basic. Non-OIDC Custom defaults to post. Secret-based
methods require a configured client secret. Public-client `none` sends the
client ID without a secret, and basic percent-encodes the client ID/secret
before building the HTTP Basic header.

Token templates supply their own form protocol and permit only the post
method. Unknown methods and nonempty method overrides on built-in vendor
adapters are rejected rather than saved and ignored. `private_key_jwt`, mTLS,
encrypted ID tokens and OIDC hybrid/implicit response flows are not implemented.

## Custom HTTP headers

Generic OAuth/OIDC consumes `http_headers` on discovery, token and UserInfo
requests. The API accepts a header object or its JSON string representation.
The encoded map is at most 32768 bytes with at most 64 entries; names are at
most 256 bytes and values at most 16384 bytes. Invalid names/values, duplicate
case-insensitive names and protocol/security headers such as `Host`,
`Authorization`, `Cookie`, `Content-Type`, `Accept`, connection/proxy headers,
`Origin`, `Referer`, `Forwarded`, `X-Forwarded-*` and `Sec-*` are rejected.
Built-in vendor adapters explicitly reject nonempty custom headers.

For discovery, custom headers are sent only to the configured issuer and
explicit server endpoint origins. A document selecting another token/UserInfo
origin is rejected when custom headers are present, rather than forwarding
credentials to that origin. Header values are not included in request errors.

## UserInfo mapping

The map has the form **destination field → source object path**:

```json
{
  "id": "data.employee.id",
  "username": "data.employee.login",
  "displayName": "data.employee.name",
  "email": "data.employee.email",
  "emailVerified": "data.employee.emailVerified",
  "phone": "data.employee.phone",
  "phoneVerified": "data.employee.phoneVerified",
  "avatarUrl": "data.employee.picture"
}
```

These are the eight supported destination fields. A source path walks nested
JSON **objects**, splitting on `.`. It is not JSONPath: `$`, bracket notation,
array indexing and wildcard expressions have no special meaning. A numeric
path component can identify an object key, but does not index an array. Paths
must have nonempty components, at most 16 components and 512 bytes, with no
control characters. The encoded map is limited to 8192 bytes.

When a field is not explicitly mapped, its same-named top-level field is used
first, followed by these standard claim fallbacks:

| Destination | Fallback claims, in order |
| --- | --- |
| `id` | `sub` |
| `username` | `preferred_username`, `name`, `sub` |
| `displayName` | `name`, `preferred_username` |
| `email` | `email` |
| `emailVerified` | `email_verified` |
| `phone` | `phone_number` |
| `phoneVerified` | `phone_number_verified` |
| `avatarUrl` | `picture` |

Missing or unusable optional mappings can use these standard fallbacks.
An **explicit `id` mapping is authoritative**: a missing path, null, object,
array, empty subject, control characters or the placeholder `unknown` causes
authentication to fail. Casdog does not silently substitute another identity
claim. Subjects must be strings or JSON integers within the signed/unsigned
64-bit range; floating-point and boolean identities are rejected. Integer
subjects retain their exact decimal value. Send larger identifiers as strings
to avoid precision loss. Subjects are limited to 512 bytes.

A missing username falls back to the subject. For a new social account, a
mapped username is adopted only when it passes local username validation and
is unoccupied in the organization. Otherwise a generated name is used. A
username collision never binds the external identity to the existing account.

New accounts save the mapped display name, email, phone and avatar. Verification
claims are true only for the exact value `true` (JSON boolean or string).
`emailVerified: true` requires a valid email; `phoneVerified: true` requires a
valid international number beginning with `+` and without an extension. Invalid
verified contacts reject the profile. The complete mapped profile is retained
under `users.properties.oauth_profile`, including the provider's
`phoneVerified` claim. That claim does **not** enroll or enable local SMS MFA;
there is no separate persistent local `phone_verified` column.

The existing local account's email, phone, verification state and MFA contacts
are preserved when signing in through an already linked identity. Matching an
email address never automatically merges or links accounts. Linking requires
the existing authenticated account, a recent session and a successful external
provider proof. Identities are namespaced by the Provider configuration ID.

Additional profile limits are: username 512 bytes, display name 255 Unicode
characters, email 255 bytes, phone 50 bytes and avatar URL 512 bytes. Avatar URLs
must be HTTP(S) without credentials or a fragment. Nonempty custom mappings on
built-in vendor adapters are rejected; the raw-claims mapping path is provided
by Custom/generic OAuth/OIDC.

## Scopes and built-in adapters

A nonempty `scopes` string is used for both sign-in and linking. Empty or
whitespace-only configuration keeps the adapter's existing default scopes.
Scopes are limited to 2048 bytes and cannot contain control characters.

Configured scopes are applied to GitHub, Google, Facebook, Microsoft, Apple,
GitLab, Discord, Slack, Twitter, LinkedIn, Bitbucket, Okta, WeChat and DingTalk.
DingTalk's default `openid` query is replaced when custom scopes are supplied.
Steam, Telegram, Lark and Feishu use adapters without a configurable OAuth
scope parameter; nonempty custom scopes are explicitly rejected for them.

### Okta issuer base

For Okta, `domain` is the complete HTTPS issuer base, for example:

```text
https://example.okta.com/oauth2/default
```

Its authorization-server path is preserved. Authorization, token and UserInfo
URLs append `/v1/authorize`, `/v1/token` and `/v1/userinfo` to this base. Token
exchange retains the adapter's HTTP Basic authentication behavior.

Resolution priority is `domain`, then `issuer_url`. These explicit bases reject
query parameters, fragments and userinfo. For older configurations only,
`custom_auth_url` remains a fallback: its HTTPS origin is used with `/oauth2`,
discarding the old authorization URL's path. Other custom endpoint fields do
not override Okta's derived `/v1/*` routes. Configure a real base; the legacy
placeholder host is not a usable provider.

## Network access and approvals

Generic and configurable Okta server requests resolve and validate DNS answers,
pin the checked addresses, disable ambient HTTP proxies and redirects, and
enforce connection/request timeouts. Token and UserInfo responses must succeed
at HTTP level and contain valid bounded JSON. Failure responses are not treated
as credentials, and request errors do not echo tokens or client secrets.

Private network access is denied by default. Provider ownership, including an
owner named `admin`, does not grant an exception. A **current real global
administrator** must explicitly approve the current configuration through:

```text
POST   /api/providers/<id>/network-approval
       {"allow_private": true}
GET    /api/providers/<id>/network-approval
DELETE /api/providers/<id>/network-approval
```

These management endpoints require global administrator authorization. The
approval is stored server-side and binds the exact configuration fingerprint
and a new random generation on each approval. The fingerprint includes the
provider identity, client credentials, endpoints, scopes, mapping, custom headers and
issuer/domain configuration. Editing that configuration makes the approval
stale; deleting and recreating an approval does not revive an old flow.

Browser state and completion proofs bind both the configuration and the
approval generation. Casdog rechecks them before token exchange, before
UserInfo retrieval, before linking, and during completion/MFA redemption.
Relevant rows are locked during final state changes. Revocation or a changed
mapping requires starting sign-in again. Older pending proofs created without
these bindings fail closed after an upgrade; their normal lifetime is at most
five minutes. They are not upgraded into authenticated sessions.

Server requests have a 3-second DNS lookup timeout, a 2-second connection
timeout and an 8-second request timeout. Each JSON response is limited to
1 MiB; authorization codes are limited to 8192 bytes and access tokens to
16384 bytes. Control characters and empty access tokens are rejected except
that verified ID-token-only identity does not require an access token. TLS
certificate verification remains enabled.

The phase16 configuration fingerprint uses version 3 and includes token client
authentication and secondary client credentials. Existing private-network
approvals and pending OAuth proofs from the previous version become stale;
a global administrator must approve the current configuration again and users
must restart pending sign-in/linking flows.

## Supported surface and regression evidence

This implementation maps **raw UserInfo JSON** obtained through a real token
exchange or signature-verified ID-token claims. Explicit endpoint templates,
issuer discovery and signed ID-token-only identity are supported as described
above; authentication by decoding an unverified `id_token` is not.

`provider_oauth_tests` contains mapping/scope/Okta-base checks, real HTTP
transport failure cases, and PostgreSQL API regressions that create providers
and obtain network approval through the normal APIs. Database cases require a
new disposable PostgreSQL database migrated through
`049_provider_transport.sql` (including the preceding network-approval migration); do not point them at production. Run with
`CASDOG_TEST_DATABASE_URL` set, including ignored tests. A passing build alone
is not evidence that OAuth exchange, profile persistence, linking, MFA or
approval revocation passed their runtime regressions.

`oauth_endpoint_tests` adds real HTTP template/discovery protocol checks and
PostgreSQL regressions for normal Provider creation/approval, cross-instance
PKCE completion, endpoint snapshots, revocation, tenant isolation and avoiding
automatic email linking. These tests also require a disposable migrated
database and explicit execution of ignored cases.

`oidc_identity_tests` adds real RSA/P-256 signature and public-key validation,
discovery/basic/post/public-client HTTP exchanges, ID-token-only identity,
UserInfo subject agreement and PostgreSQL regressions for durable nonce,
cross-instance completion, tenant isolation, account linking, MFA and approval
revocation between separate network requests.
