# OAuth Provider configuration and sign-in

Configure an OAuth provider through the normal Provider API or administration
page, then enable its qualified `owner/name` entry in an application. Sign-in
and explicit account linking use the same configured scopes, browser-bound
state, provider identity and current configuration checks.

## Native configuration

The native Provider API accepts `custom_auth_url`, `custom_token_url`,
`custom_user_info_url`, `scopes` and `user_mapping`. `user_mapping` accepts either
a JSON object or a JSON string encoding that object. The stored representation
is JSON text; the native response exposes the mapping as an object. Compatibility
requests also accept the corresponding camelCase field names.

For a `Custom` provider, and for the explicit-endpoint generic OAuth/OIDC path,
provide all three URLs. URLs must be HTTP(S), have a host, contain no userinfo or
fragment, and be at most 4096 bytes. Existing authorization URL query parameters
are retained; Casdog replaces its own `client_id`, `redirect_uri`,
`response_type`, `state` and `scope` parameters rather than adding duplicates.
The callback destination is generated by Casdog and cannot be overridden by a
caller-supplied redirect URI.

## UserInfo mapping

The map has the form **destination field → source object path**:

```json
{
  "id": "data.employee.id",
  "username": "data.employee.login",
  "displayName": "data.employee.name",
  "email": "data.employee.email",
  "emailVerified": "data.employee.emailVerified",
  "phone": "data.employee.phone",
  "phoneVerified": "data.employee.phoneVerified",
  "avatarUrl": "data.employee.picture"
}
```

These are the eight supported destination fields. A source path walks nested
JSON **objects**, splitting on `.`. It is not JSONPath: `$`, bracket notation,
array indexing and wildcard expressions have no special meaning. A numeric
path component can identify an object key, but does not index an array. Paths
must have nonempty components, at most 16 components and 512 bytes, with no
control characters. The encoded map is limited to 8192 bytes.

When a field is not explicitly mapped, its same-named top-level field is used
first, followed by these standard claim fallbacks:

| Destination | Fallback claims, in order |
| --- | --- |
| `id` | `sub` |
| `username` | `preferred_username`, `name`, `sub` |
| `displayName` | `name`, `preferred_username` |
| `email` | `email` |
| `emailVerified` | `email_verified` |
| `phone` | `phone_number` |
| `phoneVerified` | `phone_number_verified` |
| `avatarUrl` | `picture` |

Missing or unusable optional mappings can use these standard fallbacks.
An **explicit `id` mapping is authoritative**: a missing path, null, object,
array, empty subject, control characters or the placeholder `unknown` causes
authentication to fail. Casdog does not silently substitute another identity
claim. Subjects must be strings or JSON integers within the signed/unsigned
64-bit range; floating-point and boolean identities are rejected. Integer
subjects retain their exact decimal value. Send larger identifiers as strings
to avoid precision loss. Subjects are limited to 512 bytes.

A missing username falls back to the subject. For a new social account, a
mapped username is adopted only when it passes local username validation and
is unoccupied in the organization. Otherwise a generated name is used. A
username collision never binds the external identity to the existing account.

New accounts save the mapped display name, email, phone and avatar. Verification
claims are true only for the exact value `true` (JSON boolean or string).
`emailVerified: true` requires a valid email; `phoneVerified: true` requires a
valid international number beginning with `+` and without an extension. Invalid
verified contacts reject the profile. The complete mapped profile is retained
under `users.properties.oauth_profile`, including the provider's
`phoneVerified` claim. That claim does **not** enroll or enable local SMS MFA;
there is no separate persistent local `phone_verified` column.

The existing local account's email, phone, verification state and MFA contacts
are preserved when signing in through an already linked identity. Matching an
email address never automatically merges or links accounts. Linking requires
the existing authenticated account, a recent session and a successful external
provider proof. Identities are namespaced by the Provider configuration ID.

Additional profile limits are: username 512 bytes, display name 255 Unicode
characters, email 255 bytes, phone 50 bytes and avatar URL 512 bytes. Avatar URLs
must be HTTP(S) without credentials or a fragment. Nonempty custom mappings on
built-in vendor adapters are rejected; the raw-claims mapping path is provided
by Custom/generic OAuth/OIDC.

## Scopes and built-in adapters

A nonempty `scopes` string is used for both sign-in and linking. Empty or
whitespace-only configuration keeps the adapter's existing default scopes.
Scopes are limited to 2048 bytes and cannot contain control characters.

Configured scopes are applied to GitHub, Google, Facebook, Microsoft, Apple,
GitLab, Discord, Slack, Twitter, LinkedIn, Bitbucket, Okta, WeChat and DingTalk.
DingTalk's default `openid` query is replaced when custom scopes are supplied.
Steam, Telegram, Lark and Feishu use adapters without a configurable OAuth
scope parameter; nonempty custom scopes are explicitly rejected for them.

### Okta issuer base

For Okta, `domain` is the complete HTTPS issuer base, for example:

```text
https://example.okta.com/oauth2/default
```

Its authorization-server path is preserved. Authorization, token and UserInfo
URLs append `/v1/authorize`, `/v1/token` and `/v1/userinfo` to this base. Token
exchange retains the adapter's HTTP Basic authentication behavior.

Resolution priority is `domain`, then `issuer_url`. These explicit bases reject
query parameters, fragments and userinfo. For older configurations only,
`custom_auth_url` remains a fallback: its HTTPS origin is used with `/oauth2`,
discarding the old authorization URL's path. Other custom endpoint fields do
not override Okta's derived `/v1/*` routes. Configure a real base; the legacy
placeholder host is not a usable provider.

## Network access and approvals

Generic and configurable Okta server requests resolve and validate DNS answers,
pin the checked addresses, disable ambient HTTP proxies and redirects, and
enforce connection/request timeouts. Token and UserInfo responses must succeed
at HTTP level and contain valid bounded JSON. Failure responses are not treated
as credentials, and request errors do not echo tokens or client secrets.

Private network access is denied by default. Provider ownership, including an
owner named `admin`, does not grant an exception. A **current real global
administrator** must explicitly approve the current configuration through:

```text
POST   /api/providers/<id>/network-approval
       {"allow_private": true}
GET    /api/providers/<id>/network-approval
DELETE /api/providers/<id>/network-approval
```

These management endpoints require global administrator authorization. The
approval is stored server-side and binds the exact configuration fingerprint
and a new random generation on each approval. The fingerprint includes the
provider identity, client credentials, endpoints, scopes, mapping and
issuer/domain configuration. Editing that configuration makes the approval
stale; deleting and recreating an approval does not revive an old flow.

Browser state and completion proofs bind both the configuration and the
approval generation. Casdog rechecks them before token exchange, before
UserInfo retrieval, before linking, and during completion/MFA redemption.
Relevant rows are locked during final state changes. Revocation or a changed
mapping requires starting sign-in again. Older pending proofs created without
these bindings fail closed after an upgrade; their normal lifetime is at most
five minutes. They are not upgraded into authenticated sessions.

Server requests have a 3-second DNS lookup timeout, a 2-second connection
timeout and an 8-second request timeout. Each JSON response is limited to
1 MiB; authorization codes are limited to 8192 bytes and access tokens to
16384 bytes. Control characters and empty access tokens are rejected. TLS
certificate verification remains enabled.

## Supported surface and regression evidence

This implementation maps **raw UserInfo JSON** obtained through a real token
exchange. It requires explicit endpoints for the generic OAuth/OIDC path. It
does not implement Casdoor URL placeholder templates, issuer discovery, or
authentication by decoding an `id_token`. Do not describe those additional
protocols as verified by these changes.

`provider_oauth_tests` contains mapping/scope/Okta-base checks, real HTTP
transport failure cases, and PostgreSQL API regressions that create providers
and obtain network approval through the normal APIs. Database cases require a
new disposable PostgreSQL database migrated through
`048_oauth_network_approvals.sql`; do not point them at production. Run with
`CASDOG_TEST_DATABASE_URL` set, including ignored tests. A passing build alone
is not evidence that OAuth exchange, profile persistence, linking, MFA or
approval revocation passed their runtime regressions.
